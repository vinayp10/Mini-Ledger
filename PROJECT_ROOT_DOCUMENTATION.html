2. Architecture & Design Decisions

The platform follows modern layered Clean Architecture principles separated into presentation, API controller, business middleware, and persistence layers.

Smart Zero-Config Persistence

To ensure evaluators and interviewers can run the project immediately without configuring or starting a local MongoDB service:

  • The database connector (server/config/db.js) attempts to connect to local/remote MongoDB.
  • If the external MongoDB daemon is offline, it automatically launches an embedded in-memory MongoDB engine (mongodb-memory-server) seamlessly.
  • This guarantees 100% zero-downtime testability for any interview panel.

Real-time Overdue Detection

Rather than relying solely on asynchronous background cron schedulers that can fall out of sync, the system implements just-in-time state evaluation:

  • On every summary or loan query (GET /api/loans and GET /api/loans/summary), the server automatically queries for loans where dueDate < now and status === 'pending', atomically shifting their state to 'overdue'.
  • The frontend independently evaluates dates via date-fns for instant local rendering.

6. Technical Interview Q&A Cheatsheet

Q1: How do you prevent replay attacks in the Phone + OTP flow?
When an OTP is submitted to /api/auth/verify-otp, we check the expiration timestamp against Date.now(). Immediately upon a successful match, the user document in the database resets otp = null and otpExpiresAt = null before issuing the JWT. This guarantees that an OTP cannot be captured and replayed a second time.
Q2: How is the overdue calculation handled efficiently?
We use a dual-tier approach: database-side bulk update before fetching via Loan.updateMany({ user: userId, status: 'pending', dueDate: { $lt: new Date() } }, { $set: { status: 'overdue' } }), combined with client-side real-time rendering. This guarantees both accurate SQL/MongoDB summary aggregations and instantaneous UI highlighting without requiring separate batch jobs.
Q3: How are file uploads secured against exploits?
Multer checks strict MIME-type boundaries (allowing only image extensions), rejects files exceeding 5MB, and assigns random collision-free filenames. When a loan record is deleted, the backend synchronously checks the file system and unlinks the corresponding image file to prevent orphaned disk usage.
